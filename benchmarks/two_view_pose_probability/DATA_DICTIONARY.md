# VAL-018 operational-variable data dictionary

Status: frozen E1 dictionary. This document distinguishes what a capture
operator can know from what exists only in a reference/evaluation system.

Every record describes exactly one unordered pair of two spherical images.
Dataset identity is retained for evaluation and heterogeneity analysis, never
as an operational model input.

## Availability classes

- **controlled**: deliberately chosen by the capture operator;
- **visible**: directly observable from the images, masks or sensor preview;
- **derived-visible**: deterministically derived from controlled or visible
  quantities;
- **capture-system**: available only when a scanner, tracker or registered
  depth system supplies it before the RGB relative-pose estimator runs;
- **post**: generated by detection, matching or pose estimation;
- **reference-only**: depends on the evaluation pose, geometric truth or
  reference correspondences and is forbidden as a model input.

The first four classes are eligible for an explicitly named capture-model
variant. A variable is not silently imputed when a dataset lacks it.

## Capture-model variables

| Field | Class | Operator interpretation | Matterport360 | Stanford2D3D | P74 | Model use |
|---|---|---|---:|---:|---:|---|
| `baseline_m` | controlled / capture-system | Planned distance between stations, or distance reported by an external tracker | complete | complete | complete | Common geometry model; deployment requires a planned/measured baseline independent of the reference pose |
| `representative_scene_distance_m` | visible with depth | Harmonic median radial scene distance | complete | complete | unavailable in frozen table | Depth-enabled public-corpus model only |
| `baseline_depth_ratio` | derived-visible | Baseline divided by representative distance | complete | complete | unavailable | Depth-enabled public-corpus model only |
| `predicted_parallax_deg` | derived-visible | Fronto-parallel midpoint approximation `2 atan(baseline/(2 distance))` | complete | complete | unavailable | Depth-enabled public-corpus model only; it is not estimator parallax |
| `rgb_similarity` | visible proxy | Pairwise appearance similarity available from the two images | complete | complete | not yet computed | RGB public-corpus model; never described as spatial overlap |
| `registered_cloud_overlap_min` | capture-system | Minimum directional overlap of two registered point clouds within the frozen proximity rule | complete | complete | complete | Primary scanner-assisted geometry model and difficulty-response analysis |
| `registered_cloud_overlap_symmetric` | capture-system | Symmetric registered-cloud overlap | complete | complete | complete | Secondary sensitivity analysis |
| `registered_covisible_fraction_symmetric` | capture-system | Symmetric fraction of reference-visible cloud support | unavailable | unavailable | complete | Secondary P74 sensitivity analysis |

`baseline_m` in the frozen corpora was recovered from dataset station geometry.
It represents an operationally plausible planned/measured distance, but the
paper must state that the archived value is reference-derived. A deployment
that cannot measure baseline before pose estimation cannot use this model.

Registered-cloud overlap is valid as an operator-visible variable only for a
capture system that already registers depth/cloud data into a shared frame. For
a pure RGB capture it is a reference difficulty variable, not an available
input. An RGB-only release rule therefore needs an independently validated
online overlap proxy; none is silently substituted here.

For Matterport360 and Stanford2D3D, overlap uses 4,096 approximately equal-area
ERP samples per radial depth image, transforms them by the archived
`T_world_from_camera`, and measures both nearest-neighbour directions at 0.25 m.
The pairwise transform reconstructed from the two world poses is required to
agree with the frozen pair reference to `1e-6` maximum absolute error. P74 uses
the same 0.25 m intersection concept over 6,000 samples from its native scanner
XYZ raster. Sampling modalities differ and are disclosed as a domain effect.

## Post-processing variables

| Block | Fields | Availability |
|---|---|---|
| Support | `match_count`, `inlier_count`, `inlier_ratio` | common to all three corpora |
| Existing score | `raw_quality_score` | returned poses; historical quality implementation differs by run |
| Descriptor ambiguity | `descriptor_distance_median` | P74 only in current artifacts |
| Geometry | `median_parallax_deg`, `cheirality_ratio` | returned poses in all corpora |
| Residuals | `median_residual_deg`, `p90_residual_deg` | Matterport360/Stanford historical quality report only |
| Angular coverage | `coverage_entropy_a/b`, `occupied_cells_a/b` | Matterport360/Stanford only |
| Stability | `stability_success_fraction`, rotation/translation P90 | Matterport360/Stanford only |
| Model competition | `essential_score_margin`, `preferred_model_essential` | Matterport360/Stanford only |
| Runtime | total and available extraction/matching/pose stages | total common; stage timing P74 only |

The primary cross-dataset post-processing model is consequently restricted to
the common support, raw-score, parallax and cheirality fields. Richer
public-corpus and P74-specific variants are named ablations, not missing-value
imputations presented as one universal model.

## Outcomes and forbidden fields

| Field | Definition | Permitted as predictor? |
|---|---|---|
| `returned` | finite rotation and unit translation direction returned | outcome only |
| `accepted` | unchanged public quality policy accepts the returned pose | outcome only |
| `primary` | rotation <=15 degrees and oriented translation <=30 degrees | no |
| `strict` | rotation <=5 degrees and oriented translation <=10 degrees | no |
| `precise` | rotation <=1 degree and oriented translation <=5 degrees | no |
| `usable` | `accepted AND precise` | no |
| `catastrophic_accepted` | `accepted AND NOT primary` | no |
| rotation/translation error | comparison with the reference relative pose | no |
| `rotation_change_deg` | relative reference rotation in the archived evaluator | reference-only; excluded |
| reference/epipolar match correctness | requires the true relative pose | reference-only; excluded |

## Method heterogeneity

The Matterport360 and Stanford2D3D predictions come from the frozen historical
public RGB run `panorai-geo008-0f7c07e-cfa4cc1-257f190`. P74 uses the later
optimized spherical DoG + tangent DoG + RootSIFT profile
`coarse-spherical-tangent-dog-rootsift-d1p5`. This is a real domain-and-method
shift. Models must report per-dataset performance and leave-one-dataset-out
transfer; pooled pair-weighted performance cannot be presented as evidence that
one frozen frontend generalizes across all domains.

A confirmatory release claim ultimately requires E8 to rerun one frozen public
frontend and estimator configuration prospectively on new independent groups.
